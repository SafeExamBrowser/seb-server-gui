# Sweep: form-field composables must pass static i18n keys, not prefix helpers

Status: done
Category: enhancement

## Problem

While implementing issue 01 (2026-07-28) six `use*FormFields.ts` composables
turned up that define a module-level `t` helper wrapping `i18n.global.t` with a
key prefix, e.g.:

```ts
const t = (key: string) => i18n.global.t(`institutions.${key}`);
```

They comply with the "composables use `i18n.global.t`" rule, but violate the
other i18n rule in `.claude/rules/client.md`: avoid generating i18n keys
programmatically — pass static strings to the translation function. The
prefixed keys are invisible to a plain grep for the full key, which makes
translations hard to trace (and confused the issue-01 sweep audit).

## Inventory (as of 2026-07-28)

All paths relative to `client/src/pages/`, prefix in parentheses:

- `(app)/assessment-tool/composables/useAssessmentToolFormFields.ts` (`assessmentToolConnections.`)
- `(app)/connection-configuration/composables/useConnectionConfigurationFormFields.ts` (`connectionConfigurations.`)
- `(app)/institution/composables/useInstitutionFormFields.ts` (`institutions.`)
- `(app)/user-account/composables/useChangePasswordFormFields.ts` (`userAccount.changePassword.`)
- `(app)/user-account/composables/useUserAccountFormFields.ts` (`userAccount.`)
- `(public)/register/composables/useRegisterFormFields.ts` (`userAccount.fields.<key>.label` — wraps the key in the middle)

## Scope boundary

This issue covers **only** the six module-level `t` prefix helpers above.
Every other form of programmatically generated i18n key (prefix-passing
dialog widgets, enum/value-driven lookups, etc.) belongs to
`.scratch/static-i18n-keys/issues/01-static-i18n-keys.md`, which will be
implemented **after** this issue. The two must not overlap: that issue's
inventory excludes these six helpers, and this issue touches nothing beyond
them — including the dynamic `lmsTypes.${value}` tail, which is flagged here
but resolved there.

## Fix shape

Mechanical, per file: delete the local `t` helper and replace each `t("x.y")`
call with `i18n.global.t("<prefix>.x.y")`, inlining the full static key.
For `useRegisterFormFields.ts` the key goes into the middle of the pattern:
`t("name")` becomes `i18n.global.t("userAccount.fields.name.label")`.

Watch for genuinely dynamic keys (e.g. `t(\`lmsTypes.${value}\`)` in
`useAssessmentToolFormFields.ts:85`): the prefix inlines, but the dynamic tail
stays — flag any of these in the PR rather than silently keeping them.

## Acceptance

- `grep -rn "const t = " client/src --include=*.ts` returns nothing.
- All translation calls in these six files pass full static keys (except
  explicitly flagged dynamic ones).
- `vue-tsc --noEmit`, ESLint, and Prettier pass.
- Spot-check the affected forms in the browser (assessment-tool,
  connection-configuration, institution, user-account create/edit,
  change-password, public register): labels still render translated.

## Agent Brief

> *This was generated by AI during triage.*

**Category:** enhancement
**Summary:** Inline full static i18n keys in the six form-field composables that currently wrap `i18n.global.t` with a module-level prefix helper

**Current behavior:**
Six `use*FormFields.ts` composables (inventoried above) each define a
module-level `const t = (key: string) => i18n.global.t(\`<prefix>.${key}\`)`
helper and pass partial keys to it. The full translation keys never appear in
the source, so a grep for a complete key (e.g. `institutions.fields.name.label`)
finds nothing. This violates the i18n rule in `.claude/rules/client.md`:
pass static strings to the translation function; don't generate keys
programmatically.

**Desired behavior:**
Each of these composables calls `i18n.global.t("<full.static.key>")` directly
with the complete key inlined, and the local `t` helper is deleted. The
rendered translations are byte-for-byte unchanged — this is a pure
refactor. For the register form fields, the partial key sits in the middle of
the pattern: `t("name")` becomes
`i18n.global.t("userAccount.fields.name.label")`.

**Key interfaces:**
- The module-level `t` prefix helpers — delete them; they are the only thing
  this issue removes
- `i18n.global.t` from `@/i18n` — the one translation entry point these
  composables should call, per the client i18n rules
- One genuinely dynamic key exists: the assessment-tool composable builds
  `lmsTypes.${value}` from the `LMS_TYPES` schema enum. Inline the prefix so it
  reads `i18n.global.t(\`assessmentToolConnections.lmsTypes.${value}\`)`, keep
  the dynamic tail, and flag it in the PR description. Flag (don't silently
  keep) any other dynamic keys encountered.

**Acceptance criteria:**
- [ ] `grep -rn "const t = " client/src --include=*.ts` returns nothing
- [ ] Every translation call in the six composables passes a full static key,
      except the explicitly flagged dynamic `lmsTypes` case
- [ ] `vue-tsc --noEmit`, ESLint, and Prettier pass in `client/`
- [ ] Browser spot-check: the affected forms (assessment-tool,
      connection-configuration, institution, user-account create/edit,
      change-password, public register) still render translated labels, not
      raw keys

**Out of scope:**
- Renaming or restructuring any translation keys or locale files — keys stay
  exactly as they resolve today
- Touching translation calls that already pass full static keys (e.g.
  `validation.required`, `validation.passwordsMatch`)
- The template/`$t` and `useI18n()` conventions elsewhere in the codebase
  (covered by `01-i18n-global-t-sweep.md` in this feature)
- **Any other programmatically generated i18n keys** — prefix-passing dialog
  widgets (`DeleteConfirmDialog` and friends), enum/value-driven lookups, and
  the dynamic `lmsTypes.${value}` tail left behind here. All of that belongs
  to `.scratch/static-i18n-keys/issues/01-static-i18n-keys.md`, which is
  scheduled after this issue. Do not fix those "while you're in there."
