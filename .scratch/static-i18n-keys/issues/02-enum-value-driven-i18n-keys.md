# Replace enum/value-driven i18n key lookups with explicit key records

Status: done

## Problem

Split out of `01-static-i18n-keys.md` during triage (2026-07-28) so it can be
triaged and scheduled independently of the Class 1 (prefix-passing widget)
sweep.

`.claude/rules/client.md` says to pass static strings to the translation
function. A handful of call sites build keys from a runtime enum value
(`t(\`...types.${item.type}\`)`). The value domain is a finite enum, so the
risk is lower than the prefix-passing APIs, but the keys are still invisible to
grep-based tooling — an unused-key sweep would delete them from `en.json`
without any source hit (this is exactly what bit us in SEBSERV-958, see
issue 01).

## Inventory (as of 2026-07-27)

- `components/widgets/indicatorsTable/IndicatorsTable.vue`
- `components/widgets/clientGroupsTable/ClientGroupsTable.vue` + `composables/useFormFieldsBasic.ts`
- `pages/(app)/user-account/composables/useUserAccountFormFields.ts` (`general.userRoles.${value}`)
- `pages/(app)/assessment-tool/composables/useAssessmentToolFormFields.ts`
  (`lmsTypes.${value}` from the `LMS_TYPES` enum; after
  `.scratch/i18n-in-composables/issues/02-static-i18n-keys-in-form-fields.md`
  inlines the prefix this reads `assessmentToolConnections.lmsTypes.${value}`)
- `pages/(app)/user-account/components/UserAccountForm.vue` (`role.info.${role.value}`)
- `pages/(app)/monitoring/[examId]/components/dialogs/AskDialog.vue` (`statuses.${value}`)

## Proposed fix shape

Replace each dynamic lookup with an explicit value→static-key record, e.g.

```ts
const userRoleLabelKeys: Record<UserRole, string> = {
    [UserRole.SEB_SERVER_ADMIN]: "general.userRoles.SEB_SERVER_ADMIN",
    // ...
};
```

so every en.json key appears verbatim somewhere in `client/src`.

The codebase already uses this idiom — see `STRATEGY_LABEL_KEYS`
(`Record<ScreenProctoringCollectionStrategy, string>`) in
`BoxScreenProctoringSettings.vue` and `clientOSLabels`
(`Record<ClientOSLimited, string>`) in `getSummaryClientGroups.ts`. Follow it.

Site-specific notes (verified against en.json 2026-07-28):

- **User role description (`UserAccountForm`)**: `userAccount.general.role.info`
  has keys for only four roles; `USER_ROLES` (zod-schema-derived) also contains
  `TEACHER`, so a teacher selection already produces a missing-key fallback
  today. Decision (Alain, 2026-07-28): this change must be
  behavior-preserving — don't fix and don't worsen the pre-existing gap. Keep
  the record exhaustive over `UserRole` and map `TEACHER` to the static string
  `"userAccount.general.role.info.TEACHER"`; vue-i18n falls back identically
  before and after.
- **ASK dialog statuses**: the value domain is the union
  `"ALL" | ConnectionStatusEnum`, not a bare enum — the record covers that
  union (`en.json` has an `ALL` entry).

## Agent Brief

**Category:** enhancement
**Summary:** Replace enum/value-driven i18n key template literals with
explicit value→static-key records so every consumed en.json key appears
verbatim in source.

**Current behavior:**
Six call sites (inventory above) build translation keys at runtime from a
finite enum/union value, e.g. `` t(`general.userRoles.${value}`) ``. The keys
resolve correctly, but no source file contains the full key strings, so
grep-based tooling (unused-key sweeps) would delete them from `en.json`.

**Desired behavior:**
Each inventoried site looks its label up in an explicit
`Record<ValueType, string>` whose values are full static key strings, then
passes that static key to the translation function. Rendered output is
byte-for-byte identical to before — this is a pure refactor. Follow the
existing idiom (`STRATEGY_LABEL_KEYS`, `clientOSLabels`).

**Key interfaces:**
- Each record's key type is the site's actual value domain, so the compiler
  enforces exhaustiveness: the indicator type enum, the client-group type enum
  (note: the en.json key set is wider than the three options offered in the
  basic form — cover what the site can render), `UserRole`, the LMS type
  union from `LMS_TYPES`, and `"ALL" | ConnectionStatusEnum` for the ASK
  dialog status filter.
- `UserRole` record: map `TEACHER` to the static string
  `"userAccount.general.role.info.TEACHER"` even though en.json lacks that key
  — preserves today's missing-key fallback exactly (see decision above).

**Acceptance criteria:**
- [ ] No template-literal key construction remains at the six inventoried
      sites (`grep -rE '\$?t\(`' client/src` — remaining hits are only the
      issue-01 prefix-passing widgets).
- [ ] Every en.json key consumed by these sites is findable by grepping its
      full string in `client/src`.
- [ ] `npx vue-tsc --noEmit`, eslint, prettier pass in `client/`.
- [ ] Browser check on the affected pages (indicators/client-group tables,
      user-account form, assessment-tool form, monitoring ASK dialog): labels
      render as before, no *new* missing-key console warnings.

**Out of scope:**
- The prefix-passing dialog/widget APIs (issue `01-static-i18n-keys.md`).
- Adding the missing `userAccount.general.role.info.TEACHER` translation or
  otherwise changing TEACHER behavior.
- Touching translation values in `en.json` — this issue changes lookup code
  only.
